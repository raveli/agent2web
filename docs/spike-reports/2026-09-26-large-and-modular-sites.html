Large and modular sites

agent2web · 2026-09-26 · commits 8373fef and 503124f on claude/static-html-mcp-hosting-ufkmai · not yet deployed

In short: a password-protected site could not be updated once its index.html reached 56 KB. Agents can now change part of a file, or upload a file in pieces, and locked sites can be split into separate CSS, JS and HTML files on their own hostname. All 131 tests pass, and the modular case was checked in a real Chromium browser.

What failed

An agent tried to update a locked site whose index.html had grown to 56 KB. Three attempts through site_update_files (base64, raw UTF-8, minified) were each cut off at about 39 KB. The agent rolled back to the last good version, and nothing broken went live.

Two causes

CauseWhat was actually true
The size of a single call The server accepts 5 MB per file. The ~39 KB limit belongs to the calling agent, which caps how much it can send in one tool call. Raising server limits cannot fix this. The only fix is for no write to need the whole file in one call.
Why the file was so large The publish warning told agents to inline all CSS and JS into one file for every password-protected site. That is only needed on path URLs (/s/<slug>/), where the page is sandboxed. On the site's own hostname, separate files work. So pages grew for no reason.

Change 1: large files

ToolWhat it doesWhen to use it
site_edit_file (new) Exact find-and-replace inside one published text file, published as a new version. Each old_text must match exactly and appear once, unless replace_all is set. If any edit fails, nothing is published. Changing part of a large page. The call is only as big as the change.
site_stage_file (new) Uploads a file in pieces to a staging area that is never served. Send the first piece with append:false, then the rest with append:true. Replacing a large file whole, or a first publish of one.
staged argument on site_publish / site_update_files Publishes the named staged files, then clears them. The step that makes a staged file live.

All write tools now tell agents to keep each call under about 20 KB and name both routes.

Design in one sentence, with the code

Every write goes through the existing updateFiles → publish path, so edits and staged uploads get the same guarantee as before: all objects are written before the site's version pointer moves, in one batch. Staging lives under staging/<slug>/ in R2, outside sites/, and is keyed by slug so a site can be assembled before it exists.

// src/store.ts: editFile, core loop
edits.forEach((edit, i) => {
  const count = text.split(edit.old_text).length - 1;
  if (count === 0) throw new UserError(`${label}old_text was not found ... Nothing was changed.`);
  if (count > 1 && !edit.replace_all) throw new UserError(`${label}old_text occurs ${count} times ...`);
  // A function replacement, so "$&" and friends in new_text stay literal.
  text = edit.replace_all
    ? text.split(edit.old_text).join(edit.new_text)
    : text.replace(edit.old_text, () => edit.new_text);
});
return this.updateFiles(slug, [{ path: file.path, content: text, encoding: 'utf8' }], [], note);

// src/store.ts: updateFiles, staged branch
if (staged.length) {
  const loaded = await this.loadStaged(site.slug, staged);
  const result = await this.updateFiles(slug, [...upsert, ...loaded], remove, note);
  await this.clearStaged(site.slug, staged);   // only after a successful publish
  return result;
}

Base64 pieces must each be a multiple of 4 characters long. atob accepts missing padding, so a piece split mid-group would silently lose bits instead of failing.

Change 2: modular locked sites

A locked page on a path URL gets a sandbox CSP. The sandbox gives it an opaque origin, and an opaque origin sends no cookies with CSS, JS or image requests, so those requests fail. On <slug>.<A2W_SITES_BASE_DOMAIN> or a custom domain there is no sandbox: same-origin files carry the unlock cookie like the page itself does.

  • Warning: fires only when a locked site has no hostname of its own, or when A2W_SITE_SANDBOX=always.
  • Redirect: a GET to the path URL of a locked site that has a hostname returns 302 to the hostname, keeping path and query. No link lands on the version where assets fail. Public sites still answer on the path URL.
  • Guidance: site_publish tells agents which case applies. With hostnames, prefer small separate files. Without them, inline.
Verified: Chromium opened /s/modular/, was redirected to modular.localhost, and was unlocked with the password. app.css and js/app.js both answered 200, the style applied and the script ran.
Design in one sentence, with the code

One predicate, hasOwnOrigin, decides whether a site can load its own files. The warning and the redirect both use it, so they can't disagree.

// src/core/urls.ts
export function hasOwnOrigin(config, site) {
  if (config.siteSandbox === 'always') return false;
  const urls = siteUrls(config, site);
  return Boolean(urls.custom ?? urls.subdomain);
}

// src/http/hosting.ts: before the password gate
if (site.visibility === 'password' && !target.hostBased &&
    (c.req.method === 'GET' || c.req.method === 'HEAD') && hasOwnOrigin(config, site)) {
  const home = siteUrls(config, site).primary.replace(/\/$/, '');
  return c.redirect(`${home}${rest}${new URL(c.req.url).search}`, 302);
}

3. After deploying, check the new tools are listed

Reconnect the MCP client and ask it to list agent2web tools. site_edit_file and site_stage_file should appear, and the site_publish description should say to prefer several small files.

4. Try a modular locked site

Publish a test site with a password and three files (index.html linking app.css and js/app.js). The response should carry no warning. Open the hostname URL, enter the password, and the styles and script should apply.

Known limits

Note: these are the limits that remain after both changes.

  • A self-hosted install with no A2W_SITES_BASE_DOMAIN and no custom domain only has path URLs. Locked sites there must still be single-file, and the warning and tool guidance say so.
  • Staged files that are never published stay in R2 until they are overwritten, or until their site is deleted. Nothing expires them automatically.
  • site_edit_file works on the current version only. If two agents edit at once, the second edit applies on top of the first, or fails if its text no longer matches.
